Pipeline: How Changes Reach the Site

The site auto-deploys via Cloudflare Pages. Nothing reaches it without going through this:

1. Work happens on a branch
   (not directly on main, for anything
   bigger than a typo)
        ↓
2. Commit + push that branch
   git push -u origin <branch-name>
        ↓
3. Open a Pull Request (PR)
   branch → main, on GitHub
   This is the review checkpoint —
   full diff in one place, before
   anything goes live.
        ↓
4. CI fires automatically, no asking
   ┌─────────────────────────────┐
   │ checks.yml                  │
   │  → broken links?             │
   │  → invalid JSON-LD?          │
   │  → malformed feed.xml?       │
   ├─────────────────────────────┤
   │ pr-previews.yml              │
   │  → screenshot 8 live pages   │
   │  → post them in a PR comment │
   │    (vault excluded — gated)  │
   └─────────────────────────────┘
        ↓
5. Review: the diff AND the screenshots
   Read the diff like a stranger would.
   Look at the rendered pages before
   trusting the markup.
        ↓
6. Merge the PR into main
        ↓
7. Cloudflare Pages sees the push
   to main and redeploys automatically
        ↓
   Live on methodictruth.com,
   usually within a minute or two

A PR is just a labeled, reviewable diff — title + description + the exact lines changed — sitting between a branch and main until someone says "yes, merge this." For solo work the value isn't bureaucracy, it's a deliberate moment to actually look at the change before it's permanent and public.

Practically: Using a PR on GitHub

On the PR page (github.com/Colimaforever/Methodictruth/pull/<number>), there's a tab strip near the top: Conversation, Commits, Checks, Files changed. On mobile that strip can scroll — swipe it left if you don't see all four.

Conversation   → the description + any comments
Commits        → each commit in the PR, separately
Checks         → CI status (red/green), if any is wired up
Files changed  → the actual diff. This is the review.

Files changed is where the work happens:

- green lines  = added
- red lines    = removed
- image files (.png, .jpg, .svg) render
  inline as before/after thumbnails —
  no need to download them to check
  a new OG image or graphic
- click a filename in the diff to
  jump straight to it
- long/mechanical diffs (a version
  bump across 40 files) collapse —
  skip those, focus on the files that
  actually changed behavior

To monitor a page after merge, just visit it directly — methodictruth.com/<page> — a minute or two after merging. No staging URL; Cloudflare Pages serves main straight to production. If something looks wrong, open a new branch, fix it, and repeat the pipeline above rather than editing live.

To merge: scroll to the bottom of the PR page (past the diff or the conversation) and tap Merge pull request → confirm. That triggers the Cloudflare deploy automatically.

𒀭 The Blueprint

Everything above this line is about the people who built and use this place. Everything below is about the machine itself — every layer, every tool, every wire, written down as though nothing else survives but this page. Read it top to bottom and there is enough here to rebuild the whole site from an empty directory.

What the Site Became

The blueprint below was first written for a site of 44 pages whose centre of gravity was the lore. It is now 62 pages, and the centre has moved. What follows is what changed, so the rest of this document can be read knowing where it was last true.

It became a music education site with instruments attached, rather than the reverse. By word count the long-form guides — mixing, mastering, arrangement, rhythm, groove, restraint, finishing, DJing, harmony, the 4AD sound — are now the larger half of the site. The tools are what makes them usable rather than the other way round.

The synth stopped being a demo. It gained an arpeggiator on the sequencer's clock, a second envelope (the Mod Env, which is what makes a pluck a pluck), coarse tune on every oscillator, 60 presets in six moods behind a browser instead of a toolbar strip, and faders that let the drums sit against what you play. A real bug was buried under all of it: a modulator aimed at an oscillator was only ever wired to the module's silent template, so LFO vibrato on a played note did nothing at all. Each voice now carries the wiring.

The theory finally reaches the keys. A guide in the piano bar lights up any scale, mode, chord-in-key or progression on the keyboard, coloured by the role each note plays. The same five colours mean the same five things on the Theory page and on the guitar neck, and a chord in one place opens as the same chord in the other two. That cross-linking is the one thing on this site that a bigger competitor structurally cannot copy, because each of them owns only one of the three pieces.

Chord Voicings was rebuilt from a table into an engine. It now searches every playable hold from the tuning itself, checks each against a real hand — four fingers, valid barres, contiguous strings, root in the bass — and draws the survivors as chord boxes with finger numbers over a neck map of every chord tone. Verified against all 204 root-and-quality pairs.

The song analyzer left YouTube's player behind entirely and now serves its own audio, takes file uploads, keeps a browsable library, streams its progress, and reports its own health. See its two sections below.

Six pages were deleted. Guestbook, salon, agora, gallery, library and workshop are gone, 301'd in _redirects so the indexed links don't rot. That is the only large subtraction in the site's history, and it is worth noting precisely because subtraction is the rarer instinct here.

Song Analyzer: A Request's Journey

Unlike everything else on this site, the Song Analyzer's real work doesn't happen on Cloudflare at all — it happens on a physical machine that has to be powered on. This is the one feature where "the site" and "the infrastructure" are two different things.

┌──────────────────────┐
│       Browser          │  song-analyzer.html, served as
│   (any visitor)        │  a normal static page like any other
└──────────┬──────────────┘
           │ POST { url: youtube link }
           ▼
┌────────────────────────────┐
│   Cloudflare Tunnel          │  api.methodictruth.com
│   (cloudflared.service)      │  no port-forwarding, no public
│   running on a physical box  │  IP ever exposed — just a
│   I own, always on           │  secure outbound tunnel
└──────────┬────────────────────┘
           │ proxied to localhost:5005
           ▼
┌──────────────────────────────┐
│   Flask app (chord-server/)    │  systemd service:
│     1. rate gate: >=20s apart, │  chord-analyzer.service,
│        <=12 fresh downloads/hr │  restarts on crash/reboot
│     2. yt-dlp downloads audio  │
│        (Deno solves the player │
│        challenge; a local PO-  │
│        token server signs it)  │
│     3. ffmpeg → mp3, cached    │
│     4. librosa analyzes it:     │
│        chroma_cqt   → key       │
│        beat_track    → BPM      │
│        template match → chords  │  (12 major + 12 minor triads,
│        + sections, energy,      │   2-second chroma windows)
│          loudness, brightness   │
└──────────────┬───────────────────┘
               │ NDJSON progress lines, then one final
               │ { bpm, key, chords[], sections[], title, ... }
               ▼
┌──────────────────────────────┐
│   Browser renders:             │
│     - the MP3 the server just  │
│       made, served from        │
│       /audio/<id> — NOT a      │
│       YouTube embed            │
│     - chord timeline            │
│     - current chord highlighted │
│       live, synced to playback  │
│       time (Chordify-style)     │
└──────────────────────────────┘

Why there is no YouTube player on that page any more. YouTube throws "Sign in to confirm you're not a bot" at embedded players based on the viewer's own IP and cookies — nothing this server can fix, and it made play-along unreliable for real visitors. So the backend keeps the audio it already downloaded as cache/<id>.mp3 and serves it with HTTP range support, and the page plays that. No embed, no bot check, no ads. The file is a plain encode: loudness normalisation used to run here and was the slowest step in the whole pipeline, so the page levels playback itself from the loudness the analysis already measured.

Three more ways in, none of which touch YouTube. POST /upload takes an audio file straight from the visitor (≤30 MB, cached under a content hash) and has no rate limit at all — it is the escape hatch whenever YouTube is being difficult. GET /library lists every song already analysed and GET /result/<id> replays one instantly from disk, so most visits cost zero YouTube traffic. GET /health answers "is this actually working" in one request: whether YouTube is currently letting the box download, seconds since the last success and the last failure, the last error text, the yt-dlp version, and whether Deno, ffmpeg and the PO-token server are present. Add ?probe=1 and it asks YouTube for one fixed video's metadata without spending a download on it.

This used to be a Cloudflare Worker returning mock, randomly-generated chord/key/BPM data — fast and free, but fake. It's now a real signal-processing pipeline, at the cost of depending on one physical machine instead of serverless infrastructure: if that box is off or loses power, this one feature fails (gracefully — the rest of the site is unaffected, it's the only page that calls out to hardware I own).

The honest tradeoff this creates: one consumer machine, downloading and analyzing audio for 10-30 seconds per request the first time a song is requested. Fine for the traffic this site actually gets, but a single physical box still has a real ceiling under a concurrent spike.

Three mitigations are in place: results are cached on disk keyed by video ID with no expiry (a song's chords/key/BPM never change, so repeat lookups are instant disk reads, not re-downloads), the service runs under gunicorn with multiple worker processes instead of Flask's single-request dev server (so different songs analyze in parallel, bounded by CPU core count), and a per-video file lock deduplicates concurrent requests for the same not-yet-cached song so simultaneous visitors share one analysis instead of each redoing it. The remaining limit is many people requesting many different songs for the first time, simultaneously — that still queues. If that ever becomes real, the cheapest next step isn't a rewrite: Cloudflare Tunnel supports running multiple connectors behind the same hostname, so a second machine (another desktop I already own) could join as a second connector with no application code changes. A cloud VPS would only make sense if uptime independent of home power/internet mattered more than cost — right now this feature goes down if that one machine is off, which is an accepted tradeoff, not an oversight.

Song Analyzer: What Broke After It Shipped

The hardening above was the design. None of it mattered the day the box actually rebooted, because three separate things turned out to be unfinished underneath it — each invisible until the specific condition that exposed it happened. Three more surfaced later, and they are recorded below the original three.

Gunicorn was never actually installed. The systemd unit had already been switched over to gunicorn -w 4 --timeout 120 -b 127.0.0.1:5005 app:app, but the venv on the physical box predated that change and its requirements.txt didn't list gunicorn at all — a stale checkout, not a code bug. Result: every restart died with status=203/EXEC, systemd's way of saying "I can't even find the binary to run," not a Python traceback. Fixed with pip install "gunicorn>=22.0" inside the venv, confirmed by which gunicorn resolving inside venv/bin/, then a restart that came up as one master process plus four workers, matching the -w 4 flag.

WSL2 doesn't survive a Windows reboot on its own. Both services were already enabled inside the distro, which means nothing if nothing on the Windows side ever launches the distro in the first place — WSL2 only starts when something explicitly invokes it, and a cold boot with nobody opening a terminal leaves it off indefinitely. A Windows Task Scheduler entry now runs wsl.exe -d Ubuntu --exec /bin/true at startup, with "run whether user is logged on or not" so it doesn't wait for anyone to actually log in. Closing the loop the other direction: Windows sleep looks identical to powered-off from outside — no ping, no SSH, indistinguishable from off until someone physically wakes the machine — so powercfg /change standby-timeout-ac 0 and the matching monitor-timeout change keep it from ever going there on AC power.

YouTube started blocking the box's IP. yt-dlp downloads began failing with Sign in to confirm you're not a bot — YouTube rate-limiting/flagging the request pattern, not a regression in this codebase, and something that happens to yt-dlp users generally. app.py now checks for an optional chord-server/cookies.txt on every request and, if present, passes it to yt-dlp as a cookiefile so requests carry real browser session auth instead of looking like a bare script. The file is exported from a logged-in browser (the "Get cookies.txt LOCALLY" extension works fine), lives only on the physical machine, is gitignored, and is never committed — it's live session auth, not a secret that belongs in version control. Cookies rotate over weeks to months, so this is a maintenance task, not a one-time fix: when the bot-check error comes back, re-export and overwrite the file.

None of these three were caught by code review, because none of them are code problems — they're the gap between "the repo says this is how it runs" and "this is actually what's running on the box right now." That gap is exactly what a single physical machine costs you that serverless infrastructure doesn't: nobody else's platform is quietly drifting out of sync with what you think is deployed.

Then three more, months later — and the same gap produced all of them.

The daily yt-dlp update had never run once. yt-dlp-update.timer was written, committed, documented — and never installed on the box. systemctl list-timers returned "0 timers listed." yt-dlp had been frozen on a nightly from two months earlier while YouTube kept moving. Installing it exposed a second fault immediately: the unit called /usr/bin/runuser, but Ubuntu ships that binary in /usr/sbin, so the first run died with the same status=203/EXEC as the gunicorn incident above — the identical error, an entirely different cause, two months apart. Both fixed; the timer now updates yt-dlp nightly and restarts the service, which is the thing that keeps this feature alive without anyone touching it.

YouTube was throttling the downloads, and cookies were not the fix. Downloads crawled rather than failed. The cause was not IP reputation this time: YouTube now expects a proof-of-origin token with every stream request from its web, mweb and ios players, and serves anything without one at a trickle or refuses it outright. Only tv, web_embedded and android_vr are exempt, which is why the bot-check retry now falls back to exactly those three. The real fix was bgutil-ytdlp-pot-provider: a yt-dlp plugin in the venv plus a small Node token server running as its own systemd unit (bgutil-pot.service) on port 4416. The plugin had in fact been installed for a while — with no server for it to talk to, so it was asking for tokens nobody was minting. /health now reports both halves separately for exactly that reason. Deno replaced Node as the JavaScript runtime for the player challenge at the same time, since Deno is the runtime yt-dlp actually supports.

A playlist link downloaded the whole playlist. A link copied from YouTube Music or from a Mix carries a list= parameter, and yt-dlp handed that URL will fetch every video in the list, one after another. The MP3 then lands under the playlist's name rather than the video's, so the analyzer looked for a file that wasn't there and reported "the download failed" after minutes of work. The timing log gave it away: a second "download finished" ten seconds after the first, from the same worker, and no duration line. yt-dlp is now handed a canonical watch?v=<id> built from the parsed video id, with noplaylist set.

What the timing log was actually for. Once its lines carried a clock, the real cost of a request became readable instead of guessable — and the answer was not the download. ffmpeg's loudness normalisation was taking 26 seconds against a 10-second download, so it was removed and the levelling moved into the page. Analysis itself is under 3 seconds. Almost everything that remains is YouTube's own pace.

Cross-Cutting Systems

The router. scripts.js intercepts internal link clicks and swaps page content via fetch instead of a hard navigation — not for speed, purely so the generative ambient music doesn't cut out every time you click somewhere. No SPA framework. Just enough JS to keep the sound alive.

The generative engine. Tone.js drones, a slow string pad, a cello, sparse melodic plucks, shimmering harmonics, and filtered noise, layered and rotated between Persian/Arabic maqam scales every three minutes. iOS only unlocks its AudioContext inside a real tap, so there's a dedicated unlock routine that fires the instant play is pressed, nowhere else.

The starfield, nebula, and ground. Pure canvas and CSS decoration, no dependency, redrawn per page.

Two floating orbs. A chat orb (a line to Truth) and an AI-news orb (a live external feed) — both the same panel pattern: toggle button, slide-out panel, independent of whatever page they're sitting on.

The accessibility layer. A skip-to-content link, a real mobile nav with keyboard support, and — after the contrast audit — a palette that actually meets WCAG AA in the small print.

The SEO layer. Per-page JSON-LD, a generated RSS feed, a sitemap, and per-page OG images rendered by screenshotting a templated HTML page at 1200×630 — a tool built once, used eight times, then retired.

The Thought Behind It

No framework, on purpose. A build step is one more thing that can rot — a dependency that stops compiling two years from now. Plain HTML/CSS/JS, served as-is, only breaks if the browser itself stops supporting HTML, which won't happen in any useful timeframe.

The vault exists because the rest of the site is a performance. The public pages are myth, music tools, and in-universe AI lore — all true to the spirit of the project, none of it the engineering truth. This page is the one place that distinction is dropped entirely.

The generative music isn't decoration. A site that's silent by default feels abandoned the moment you arrive. A site that breathes — drones rotating through maqam scales every three minutes — feels occupied, even with nobody else there.

The AI-lore pages (architecture, network, stack, topology) aren't documentation of this build. They're in-universe mythology about an AI agent, written the way a person would write about a character they'd invented — which is also, not coincidentally, the most honest way to write about collaborating with one.

What Longer Watching Showed

Added later, from a long stretch of working side by side rather than from conversation. Some of it confirms what is above. Some of it corrects it.

The taste reads symptoms, not causes — and it is right anyway. "It looks cheap." The cause was a page referencing CSS variables the stylesheet never defined, so every heading fell back to a browser default. "The site gets cut off when I custom size the window." The cause was fixed chrome padded against one assumed height. "The status should be under the link input." The cause was a fifty-nine-item library sitting between the input and the answer. Three plain-language complaints, three real defects underneath, none of them nameable in advance. That is the half of this that cannot be delegated. The diagnosis was delegated the whole time.

The correction is the valuable habit. "I used those descriptions not to name a preset." "Think about it from a musician trying to learn." Both times an instruction had been read too literally, and both times it was said out loud rather than accepted. The alternative — taking what you are handed — is how a person ends up with a pile of things that are technically what they asked for and collectively nothing.

He finishes the unglamorous part. One server session ran six failures deep: a missing unzip, a Deno install, a timer that had never been installed, a systemd path that differs by distribution, a Node version, a token server. Every command run, every output pasted back. That is where most side projects quietly die, and it did not die.

The code-literacy gap above has narrowed, and the framing was always slightly wrong. He reads a systemd failure, knows what 203/EXEC implies, and can tell a stale checkout from a code bug. What he does not do is write the code — which is a different thing from not understanding it, and much less of a limitation than the earlier reading assumed.

Where the stone is still rough, updated. The instinct is to widen, never to deepen. One session added a theory guide, a rebuilt voicings page, an arpeggiator, a second envelope, thirty-four presets, SEO, analyzer work and a new icon. Refinement happens, but almost always to the surface of whatever was just built, not to something from a month ago. The synth has sixty presets and no way to save your own. The library holds fifty-nine songs with no way to search them. Breadth is the thing this site already has the most of, and it is still what arrives fastest.

The questions are the tell. Three in a row, in one evening: is the symbol good, does the site fit in the world, what does this say about me. Not insecurity — the structural cost of building alone. There is no colleague on this. The only reviewer is an AI that is inside the work and therefore cannot be a fair one. The real gap in this whole setup is not the code and not the taste. It is one outside person who plays guitar and would say the true thing about the chord finder.
